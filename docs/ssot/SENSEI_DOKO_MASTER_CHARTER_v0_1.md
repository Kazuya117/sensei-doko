# 先生いまどこ？ MASTER CHARTER v0.1 (DRAFT 2026-10-23)

## 第 1 章 性格

### 1-1 本書の性格

本書は、アプリ「先生いまどこ？」について **何を作るのか・何を作らないのか・誰が何を決めるのか・何を約束しているのか** を 1 か所に固定する文書である。新しい思想を発明しない。アプリがすでに README・`privacy.html`・説明書（`docs/*.docx`）・データベースの定義で表明していることを、矛盾なく 1 本にまとめ、以後の変更はここを起点にする。

### 1-2 正本の優先順位

```
Priority 1 : アプリオーナーの裁定（Issue のコメントに記録する）
Priority 2 : docs/ssot/   （本書と配下 SSOT-1〜3）
Priority 3 : README.md / privacy.html / docs/*.docx   （利用者向けの写し。矛盾したら Priority 2 が勝つ）
Priority 4 : CLAUDE.md（Builder 向けの投影。本書の下流）
```

### 1-3 本書が書かないこと

- 学校の正式名称・担当教員・生徒の個人名・メールアドレス（README と `privacy.html` には学校名があるが、本書以下の正本には**書かない**。参照は「学校」「担当教員」で足りる）
- 期日・Issue 番号・閾値の変更履歴（Issue が持つ）
- 画面の文言や配色（コードが持つ）

## 第 2 章 目的・対象

### 2-1 アプリの定義

「先生いまどこ？」は、**放課後や休み時間に先生を探し回る時間をなくす** ための学内向けアプリ（PWA）である。生徒が会いたい先生を選ぶと、見かけた生徒が校内マップで場所を知らせる。先生自身が状況を知らせることもできる。

答える質問は 1 つだけである: **「いま、この先生はどこにいる可能性が高いか」**。

### 2-2 原則（AP = App Principle・上限 10・現在 8）

| ID | 条項 | enforced（機械で強制） | 出典 |
|---|---|---|---|
| **AP-1** | **目的の固定。** アプリは「探し回る時間をなくす」ために存在する。先生の行動を評価・記録する目的には使わない。広告・学外提供をしない | false（文書） | privacy.html「使いみち」 |
| **AP-2** | **AI はアプリの中で使わない。** AI は開発の道具であり、アプリの判定・表示に LLM を用いない。利用料も発生しない | false（実装上 LLM 呼び出しが無いことは付録 A-5 で実測） | README・提供価値文書 |
| **AP-3** | **先生が主導権を持つ。** 探せるのは、自分でログインして参加を選んだ先生だけ。先生は理由なしにいつでも止められ、やめると情報は消える | **true**（DB の権限・SSOT-2） | README「先生を守るための決まり」 |
| **AP-4** | **必要なときだけ・必要な人にだけ。** 場所を知らせられるのは誰かが探しているときだけ。見えるのは探している本人・先生本人・報告者だけ。居場所の一覧は作らない | **true**（SSOT-2） | 同上 |
| **AP-5** | **記録を残さない。** 報告は 2 時間で見えなくなり削除する。探した記録に場所を含めない。報告者が誰かは誰にも読めない | **true**（SSOT-2。削除の実装は付録 B Q-3 で要確認） | 同上 |
| **AP-6** | **場所と時間を限る。** 選べるのは登録済みの校内の場所だけ（保健室・トイレ・更衣室・校外は不可）。使えるのは月〜土の 7〜19 時 | **true**（`td_places.selectable`・`private.td_school_hours()`） | 同上 |
| **AP-7** | **学内の人だけ。** ログインは学校の Google アカウントと個別に許可したアドレスに限る。校内マップはログインした人にだけ届く | **true**（SSOT-2） | README「構成」 |
| **AP-8** | **約束は DB で強制する。画面側のチェックは案内に過ぎない。** 約束を変えるときは DB の定義（マイグレーション）と本書を同時に変える | — | README |

### 2-3 利用者

| 利用者 | 役割 | 参加のしかた |
|---|---|---|
| 生徒 | 探す人であり、同時に見かけた場所を教える人 | 学校アカウントでログインすれば使える |
| 先生 | 探される人。自分で状況を知らせることもできる | 自分でログインして「参加する」を押す（AP-3） |
| 運営チーム | 先生の登録・場所の管理・問い合わせ対応 | 管理者として `private.teacher_emails` を編集できる |

### 2-4 対象外（作らないもの）

本書の対象外は SSOT-1 第 3 章に列挙する。代表: 先生の居場所の常時表示・一覧／先生以外（生徒同士）の捜索／学外からの利用／AI による予測。

## 第 3 章 主体と権限

### 3-1 主体

| 主体 | 権限 |
|---|---|
| **アプリオーナー**（repo `Kazuya117/sensei-doko` の所有者・現在は PM Kazuya117 が兼務。兼務は兼務と記録する） | 本書と配下 SSOT の**批准**（PR merge）。AP の変更・データ境界の変更・不可逆変更の裁定 |

### 3-2 裁定境界

**アプリオーナーの裁定を要する**: 本書・SSOT の批准と改版 / AP-1〜8 に触れる変更 / 外部接続先の追加（Supabase 以外・通知サービス等）/ ログイン方式の変更 / データの削除期間の変更 / 本番データの一括操作 / 学校との取り決めに関わる変更。

**通常開発として進めてよい**: 上記以外。画面の改善・見本モードの充実・文言・不具合修正。ただし必ず PR 経由（第 8 章）。

### 3-3 所有境界

- 本 repo の成果物（コード・文書）はアプリオーナーの所有である。
- Supabase プロジェクトは「アイデアの種」と**共用**である（SSOT-3）。本アプリの表は `td_` で始まる。共用プロジェクトの設定変更は両アプリに影響するため、オーナー裁定とする。
- RKSTM-CORE / CTO Studio の資産（`.rkstm/` 等）は本 repo に**無い**。配布されたら CORE 所有面として扱い、編集せず還流する。

### 3-4 述べてはならないこと（保証境界）

現時点で、次のことを利用者に述べてはならない。

- 「先生の居場所は絶対に漏れない」— 約束は DB の権限で強制しているが、第三者による検証は受けていない（付録 B Q-4）
- 「報告は必ず 2 時間で削除される」— 削除の実装経路が実測で未確認（付録 B Q-3）。述べてよいのは「2 時間で見えなくなる」まで
- 「見本モードは本物の校内配置を含まない」は述べてよい（付録 A-6 で実測）

## 第 5 章 製品構造

- 画面: ビルド不要の静的サイト（HTML / CSS / JavaScript）。GitHub Pages で配信。PWA（`manifest.webmanifest`・`sw.js`）
- データ: Supabase（東京リージョン `ap-northeast-1`・Postgres 17）。プロジェクトは「アイデアの種」と共用
- ログイン: Google ログイン（学校ドメイン + 個別許可）
- 見本モード: `?demo` で起動。`app.js` 内の `demoDb` / `DEMO_PLACES` だけで動き、サーバーに送らない
- 使っていないもの: サーバー側のアプリケーション・LLM・プッシュ通知（SSOT-1 第 3 章）

## 第 6 章 データ境界（要点・詳細は SSOT-2）

- あずかる情報は 4 種類だけ: Google アカウント情報（本人確認のみ）・先生が自分で入力した情報・探した記録（場所を含まない）・見かけた報告（2 時間）
- 本アプリの表は `public.td_*` で RLS（行単位の権限）有効
- `private.*` の 4 表は RLS 無効（2026-10-23 実測・Supabase の警告）。**API から到達可能かどうかは未確認**（付録 B Q-5）

## 第 8 章 変更手続き

### 8-1 批准と改版

- 本書と SSOT の批准・改版は**アプリオーナーの PR merge**による。Builder が直接 main に書かない（branch protection で機械強制することを SSOT-3 で定める）
- 手続き: Builder または運営チームが起草 → PR → オーナー merge = RATIFIED
- 裁定を求める Issue には「既定動作」と「期限」を併記する。無回答で期限を過ぎたら既定動作で進めてよいが、批准前にオーナーの確認を取る

### 8-2 改訂トリガー

本書の次回改訂は、**アプリの実装・運用から得られた証拠**（利用の実測・不具合・学校からの要望）に基づいて行う。文書レビューのみを理由とする改訂をしない。例外: 誤記・参照切れ・文書間の不整合・オーナー裁定・法令や学校の規則の変更。v0.1 の初回起草は例外である。

### 8-3 条項予算

- AP の上限は 10（現在 8）。新設は吸収か置換で行い、純増で積み上げない
- 期日・閾値（「2 時間」「1 日 10 回」等の数値は約束の一部なので本書に書くが、変更はオーナー裁定）

### 8-4 開発規律（CTO Studio の有無に関わらず守る）

1. main へ直接 push しない。変更は PR 経由のみ
2. 完了は証拠で示す。Builder の「できました」は受理しない。CTO Studio が配布されたら `rkstm check done` を通す
3. 出典のない事実を文書に書かない。確認していないことは UNKNOWN と書く
4. 決めたことと理由を `.rkstm/memory/DECISIONS.md`（配布前は `docs/decisions/DECISIONS.md`）に日付つきで残す
5. 学校名・個人名・メールアドレス・個人の記録を repo・Issue・PR に書かない
